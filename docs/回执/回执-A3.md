## 4 · 静态量级预估（数值型模块必填）

**口径**：`hToStones` 同源 —— 1 h 当量 = `stoneHourly(level)` 灵石；材料按其**秘境产出率**折当量（`MAT_H` = `dungeon.js RESOURCE_DUNGEONS.matPerH` 的倒数：灵草 3 份/h、玄铁 2 份/h）；L47 = 炼虚，`stoneHourly(47) = 1102` 灵石/h。

| 界 | 静态日产出（当量 h/日） | 折 h/h | 折灵石/小时（L47） | 折灵石/日 | 占派遣线 |
|---|---|---|---|---|---|
| **青岚界** | **1.71**（催熟 +1 净 ＋ 小天劫 +5h/7日） | 0.071 | 78.7 | 1,889 | **7.9%** |
| **青云古界**（爬升期） | **0.33**（参悟 +1/日 − 祭炼 −2h/3日） | 0.014 | 15.3 | 367 | **1.5%** |
| **青云古界**（九阶封顶） | **1.18**（祭炼停手，参悟 ×1.18） | 0.049 | 54.2 | 1,301 | **5.5%** |
| **望族山河**（内门 · 2 兑） | **0.80**（每对 +0.4h × 2） | 0.033 | 36.7 | 881 | **3.7%** |
| **望族山河**（族长 · 4 兑） | **1.60** | 0.067 | 73.5 | 1,763 | **7.4%** |

| 对照线 | 数值 | 本批相对关系 |
|---|---|---|
| 分身派遣（既有，5 槽满） | 0.9 h/h ≈ **992 灵石/h**（`DISPATCH.baseRate 0.18 × 5`） | 单界机制为其 **1.5%~7.9%** |
| 秘境·招牌「每轮探取」（V5.1 已挂起待降档） | **6.2~7.8 万 灵石/现实小时** = 派遣线 **62~78 倍** | 单界机制约为它的 **1/790 ~ 1/1000** |
| 灵兽线（V5.6 全模块） | ≈0.034 h/h（0.82 h/日） | 同量级（青岚略高、青云略低） |
| 单界护栏（本轮新增 `MECH.dailyHCap`） | 4 h/日 | 三界上限 1.71 / 1.18 / 1.60 **全部在带内** |

**结论**：
- 三界机制**全部落在护栏带内**（最强的青岚 7.9% 派遣线），**不构成新的"主要来源"风险**；且**同一时刻只有一界机制在生效**（世界唯一），三界合计上限 4.49 h/日 = 0.187 h/h ≈ 派遣线 20.8%（这是三界同时生效的理论值，实际不可达）。
- 与 V5.1 招牌线的根因对比：招牌失控**不在单次奖励而在轮长（30 游戏天 = 现实 30 分钟）**；本批刻意把"定期"类动作锚到**现实日级**（1 现实分钟 = 1 游戏天 → 1440 游戏天 = 现实 1 日），故单次奖励可以给"看得见"的量而仍不破占比。
- ⚙ **单点旋钮**（都在 `src/data/worldMechanics.js`）：`MECH.dayGameDays`（现 1440）· 各 act 的 `cycleDays` / `cost.h` / `gain.mats` / `gain.h` · `MECH.pointPerH`（族贡折率 15/h）· `WORLD_MECHANICS[].ranks[].rate`（抽成率）。

## 7 · 9 界铺量模板说明（A4a 照此做）

**结论：新增一界 = 只改 `src/data/worldMechanics.js` 一处（追加一个参数块）；面板 / index.html / main.js / system 都不用动。**

1. **追加一个块**到 `WORLD_MECHANICS`（形状见文件头模板注释），字段：
   - 必填：`id`（＝worlds.js 同 id）· `name` · `source`（设计出处）· `exclusive` / `friction`（**照抄 `worlds.js` 原文**，自测会逐字对账）· `acts[]` · `frictionRule`。
   - `acts` 用三种 kind：`grant`（花/得，默认）· `check`（战力校验，配 `needPowerMul`）· `refine`（升阶，配 `maxLevel` / `powerPctPer` / `ratePctPer`）。
   - 成本/收入写在 `cost` / `gain`：`h`（当量灵石）· `mats: [{id, n}]`（只能用 `items.js` 既有材料）· 自定内部计分键（如 `tribute` / `jianYi`）。
   - 内部计分在块内 `points: { 键: { name, unit, hPer? } }` 注册：**只有"可花灵石买 / 可换回灵石"的计分才给 `hPer`**（参与量级估值），纯成长型计分不给（否则把进度算成财富）。
   - 周期：`cycleDays`（游戏天；缺省＝现实 1 日）· 额度：`quota: { base, perRank }`（**带额度即不吃周期冷却**，这是"职级决定额度"型机制的写法）。
2. **摩擦项**三种现成口径：`kind:'rootCost'`（已在别处生效，只做展示联动——值从 `WorldSystem` 取）· `kind:'mark'`（仅标记展示）· `kind:'tribute'`（**可开关**：`toggle:true`，走 `frictionState.tributeOn`）。
   - ⚠ 若某界要"另一种可开关摩擦"（不是族贡抽成），需在 `WorldMechanicSystem` 加一个同形开关分支（约 10 行）——**不要为单界写 if，要加就加通用的 `frictionState.<key>` 开关**。
3. **自测**（A4a 认领 `tests/V5.2.1-自测.mjs`）：每界加 3 条 —— ① `exclusive/friction` 与 worlds.js 逐字一致；② `staticDailyH ≤ MECH.dailyHCap` 且给出折灵石表；③ 每个动作"可达 + 幂等 + 额度/冷却"三态各一条。
4. **不要做的事**：不要给机制加主循环自动结算（碰公共区）· 不要新增 EconLedger 线（硬口径 8 条）· 不要让产出发境界 · 不要为单界改 `powerMulClosure`（只有"升阶型法宝"才需要战力乘区，青云已占位；新界若要战力加成，请走 `bonusView()` 的 `kind:'power'` 行 + 装配层已登记的第 6 提供方，零 main.js 改动）。
